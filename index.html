01 Что такое GitHub

GitHub — крупнейшая в мире платформа для хостинга репозиториев и совместной разработки. Она построена поверх системы контроля версий Git и добавляет к ней инструменты совместной работы: pull requests, задачи, автоматизацию, хостинг и многое другое.

Git и GitHub — в чём разница

GitGitHub
Что этоРаспределённая система контроля версий (программа)Облачная платформа-сервис вокруг Git (сайт и API)
Где работаетЛокально, на вашем компьютереВ облаке, через браузер и API
Основная функцияХранит историю изменений, ветки, слиянияСовместная работа, ревью, CI/CD, хостинг
Работает без интернета?ДаНет (но локальный Git продолжает работать)
КонкурентыMercurial, SVNGitLab, Bitbucket, Gitea
💡 Аналогия

Git — это как Microsoft Word с историей версий: работает на вашем компьютере. GitHub — это «Google Диск для кода»: туда файлы загружают, там их обсуждают, ревьюят и автоматически собирают.

02 Аккаунт и первичная настройка

Регистрация

  1. Откройте github.com/signup.
  2. Введите email, придумайте пароль и username. Имя пользователя станет частью ваших URL: github.com/username — выбирайте вдумчиво.
  3. Подтвердите email по ссылке из письма.
  4. Включите двухфакторную аутентификацию (2FA) — в 2023 году она стала обязательной для всех. Используйте приложение-аутентификатор (TOTP) или passkey.

Что стоит настроить сразу

НастройкаГдеЗачем
Аватар и имяSettings → Public profileВаше лицо в коммитах и ревью
Email для коммитовSettings → EmailsКоммиты привязываются к email; включите Keep my email addresses private, чтобы не светить личную почту
Токен (PAT)Settings → Developer settings → Personal access tokensДоступ к API и git по HTTPS вместо пароля
SSH-ключиSettings → SSH and GPG keysPush/pull без паролей (см. раздел 5)
УведомленияSettings → NotificationsНе утонуть в письмах: настройте watch-политику
Профиль-READMEРепозиторий с именем usernameКрасивая карточка на вашей странице профиля

Личный токен доступа (PAT)

Пароль от аккаунта больше не принимается при git-операциях по HTTPS. Вместо него используется токен. Два вида:

  • Classic — с наборами скоупов (repo, workflow, read:org…).
  • Fine-grained (рекомендуется) — точные права на конкретные репозитории и операции.
# Токен можно положить в git credential manager, чтобы не вводить каждый раз:
git config --global credential.helper store
⚠️ Секретность

Токен — это пароль. Не коммитьте его в репозиторий, не вставляйте в скриншоты. Если токен утёк — отзывайте его мгновенно в Settings → Developer settings.

03 Установка и настройка Git

Установка

# Windows — установщик с git-scm.com или через winget:
winget install --id Git.Git -e

# macOS — через Homebrew:
brew install git

# Ubuntu / Debian:
sudo apt update && sudo apt install git

# Fedora:
sudo dnf install git

Первичная настройка (один раз на машину)

# Имя и email, которые попадут в каждый коммит
git config --global user.name "Ваше Имя"
git config --global user.email "you@example.com"

# Ветка по умолчанию — main (современно)
git config --global init.defaultBranch main

# Полезные привычки
git config --global pull.rebase false      # pull = merge (не перематывать)
git config --global core.editor "code --wait"  # VS Code как редактор
git config --global core.autocrlf input    # концы строк

# Проверить все настройки
git config --global --list
✅ Совет

Email в git config должен совпадать с одним из email'ов, привязанных к аккаунту GitHub, — иначе коммиты не свяжутся с вашим профилем и не покажут зелёные квадратики в контрибуциях.

Проверка

git --version        # например: git version 2.47.0
git status           # проверить, что git работает в папке

04 Основы Git: коммиты и история

Три области файла

Каждый файл в Git проходит три состояния:

  • Working Directory — рабочая папка, где вы правите файлы;
  • Staging Area (index) — «корзина» подготовленных изменений, которые попадут в следующий коммит;
  • Repository — история коммитов.
рабочая папка ──git add──▶ staging ──git commit──▶ история (репозиторий)

Базовый цикл работы

# Начать репозиторий в текущей папке
git init

# Посмотреть, что изменилось
git status

# Добавить файлы в staging
git add index.html          # один файл
git add .                   # всё в текущей папке
git add -A                  # все изменения по всему проекту

# Сохранить снимок в историю
git commit -m "Добавил страницу учебника"

# Посмотреть историю
git log --oneline --graph --all
✅ Правило хорошего коммита

Один коммит = одна логическая задача. Сообщение в повелительном наклонении: «Добавить кнопку», «Исправить утечку памяти». Первая строка — до 50 символов.

Полезные команды на каждый день

КомандаЧто делает
git diffПоказывает непроиндексированные изменения
git diff --stagedИзменения, уже добавленные в staging
git show <commit>Содержимое конкретного коммита
git restore file.txtОткатить файл к последнему коммиту (undo изменений)
git restore --staged file.txtУбрать файл из staging, не теряя правки
git commit --amendДописать в последний коммит (правка сообщения/содержимого)
git reset --hard HEAD~1⚠️ Удалить последний коммит вместе с изменениями
git revert <commit>Создать коммит, отменяющий чужой коммит (безопасно)
git blame file.txtКто и когда менял каждую строку
git stash / git stash popОтложить правки в сторону / вернуть их

Файл .gitignore

Перечисляет файлы, которые Git не должен отслеживать: зависимости, артефакты сборки, секреты.

# .gitignore — пример для Node.js-проекта
node_modules/
dist/
.env
.env.local
*.log
.DS_Store
coverage/

Готовые шаблоны для любого стека: github/gitignore.

05 Удалённые репозитории и SSH

Локальный репозиторий связывается с GitHub через remote — удалённый адрес. Стандартное имя первого remote — origin.

Два способа подключения

ПротоколURLПлюсы / минусы
HTTPShttps://github.com/user/repo.gitПросто начать; требует токен при push
SSHgit@github.com:user/repo.gitНастроил ключ один раз — и никаких паролей
GitHub CLIgh repo clone user/repoСам выбирает лучший способ и авторизует вас

Настройка SSH-ключа

# 1. Сгенерировать ключ (ed25519 — современный алгоритм)
ssh-keygen -t ed25519 -C "you@example.com"

# 2. Запустить ssh-agent и добавить ключ
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# 3. Скопировать публичный ключ на Linux/macOS
cat ~/.ssh/id_ed25519.pub

# 4. Вставить его на GitHub: Settings → SSH and GPG keys → New SSH key

# 5. Проверить соединение
ssh -T git@github.com
# Приветствие: "Hi username! You've successfully authenticated..."

Клонирование и синхронизация

# Скопировать репозиторий с GitHub
git clone https://github.com/user/repo.git
cd repo

# Забрать изменения с сервера, не меняя свои файлы
git fetch origin

# Забрать и применить изменения к текущей ветке
git pull origin main

# Отправить свои коммиты на GitHub
git push origin main

# Первая публикация новой ветки со связью с удалённой
git push -u origin my-branch

# Посмотреть список remote'ов и их адреса
git remote -v
git remote add upstream https://github.com/original-author/repo.git
💡 origin vs upstream

При работе с чужим проектом (fork) origin — ваш форк, upstream — оригинальный репозиторий. Из upstream регулярно подтягивают свежие изменения.

06 Репозитории на GitHub

Создание репозитория

  1. Нажмите + в правом верхнем углу → New repository.
  2. Укажите имя, описание, выберите Public/Private.
  3. Отметьте чекбоксы: Add a README, Add .gitignore (выберите шаблон под стек), Choose a license.
  4. Create repository — и клонируйте его локально.
# Три способа из командной строки:
gh repo create my-project --public --clone
gh repo create my-project --private
gh repo create my-org/monorepo --internal

Fork — своя копия чужого проекта

Кнопка Fork создаёт копию чужого репозитория в вашем аккаунте. Это стандартный путь вносить изменения в open source: форк → ветка → правки → pull request в оригинал.

Что должно быть в хорошем репозитории

ФайлНазначение
README.mdВизитка проекта: что это, как запустить, как помочь
LICENSEЮридическая база использования кода (MIT, Apache-2.0, GPL…)
CONTRIBUTING.mdКак вносить изменения: стиль кода, процесс PR
CODE_OF_CONDUCT.mdПравила поведения сообщества
.github/ISSUE_TEMPLATE/Шаблоны багов и фич-запросов
.github/PULL_REQUEST_TEMPLATE.mdЧек-лист для авторов PR

Ключевые элементы страницы репозитория

  • Code — файлы, история, ветки; кнопки Code (клонирование), Add file (правка в браузере).
  • About — описание, топики, ссылка на сайт.
  • Insights — аналитика: traffic, contributors, код-фреквенция, зависимость-граф.
  • Watch / Star / Fork — подписка на уведомления, лайк, копия проекта.
  • Releases и Packages — версии проекта и опубликованные артефакты.

07 Ветки

Ветка — независимая линия разработки. По сути, просто подвижный указатель на коммит. Правило: никогда не работайте напрямую в main — заводите ветку на каждую задачу.

# Посмотреть все ветки (локальные и удалённые)
git branch
git branch -a

# Создать ветку и сразу переключиться на неё
git switch -c feature/search-page
# (старый синтаксис: git checkout -b feature/search-page)

# Переключение между ветками
git switch main
git switch feature/search-page

# Опубликовать ветку на GitHub
git push -u origin feature/search-page

# Удалить ветку после слияния
git branch -d feature/search-page
git push origin --delete feature/search-page

# Переименовать текущую ветку
git branch -m new-name

Стратегии именования

ПрефиксДля чегоПример
feature/Новая функциональностьfeature/dark-theme
fix/Исправление багаfix/login-timeout
hotfix/Срочный фикс в продеhotfix/security-patch
docs/Документацияdocs/api-reference
chore/Рефакторинг, зависимостиchore/update-deps

Слияние: merge и rebase

# merge: влить feature в main, создав merge-коммит (безопасно, история честная)
git switch main
git merge feature/search-page

# rebase: переставить ваши коммиты поверх main (история линейная и чистая)
git switch feature/search-page
git rebase main
⚠️ Золотое правило rebase

Не делайте rebase веток, над которыми работают другие люди (после того как вы их запушели). Переписанная история сломает их локальные копии. Rebase — только для ваших личных веток.

Защита ветки (Branch protection)

На GitHub: Settings → Branches → Add branch protection rule для main:

  • Require a pull request — запрещает прямые push'ы;
  • Require approvals — минимум 1–2 ревью;
  • Require status checks — мерж только после зелёных CI-проверок;
  • Require linear history — запрет merge-коммитов.

08 Конфликты слияния

Конфликт возникает, когда две ветки меняют одни и те же строки, и Git не может сам выбрать, чья версия правильная. Это нормально и решается за пару минут.

Как выглядит конфликт

<<<<<<< HEAD
Привет из вашей ветки
=======
Привет из чужой ветки
>>>>>>> feature/other

Алгоритм разрешения

# 1. Начать слияние — Git остановится на конфликте
git merge feature/other
# CONFLICT (content): Merge conflict in file.txt

# 2. Посмотреть файлы в состоянии конфликта
git status

# 3. Открыть файл(ы), найти маркеры <<<<<<< / ======= / >>>>>>>
#    и вручную оставить нужный вариант (или объединить оба).
#    Маркеры обязательно удалить!

# 4. Пометить конфликт как разрешённый
git add file.txt

# 5. Завершить слияние
git commit

# Передумали? Откатить всё слияние целиком:
git merge --abort
✅ Инструменты

VS Code показывает конфликты прямо в редакторе с кнопками «Accept Current / Incoming / Both». Команда git merge --continue завершает слияние после разрешения.

Профилактика

  • Чаще подтягивайте изменения: git pull origin main в своей ветке;
  • Держите ветки короткоживущими — мержите за 1–2 дня;
  • Не правьте одни и те же файлы параллельно в двух ветках.

09 Pull Requests: сердце совместной работы

Pull Request (PR) — предложение «влейте мою ветку в основную». Это место для ревью кода, обсуждения, автоматических проверок и финального слияния.

Полный жизненный цикл PR

# 1. Ветка с понятным именем
git switch -c feature/payment-api

# 2. Коммиты с осмысленными сообщениями
git commit -m "Добавить API оплаты через Stripe"

# 3. Пуш и создание PR (одной командой через gh)
git push -u origin feature/payment-api
gh pr create --title "Оплата через Stripe" --body "Closes #42"
  1. Откройте вкладку Pull requests → New pull request, выберите ветки, опишите изменения.
  2. Автопроверки (Actions) прогонят тесты — ждите зелёной галочки ✓.
  3. Коллеги делают Review: оставляют комментарии к строкам, ставят Approve / Request changes / Comment.
  4. Правки по замечаниям пушатся в ту же ветку — PR обновляется автоматически.
  5. Слияние: кнопка Merge pull request.

Три способа слияния

СпособЧто происходитКогда выбирать
Merge commitВсе коммиты ветки + merge-коммит в mainИстория важна во всей полноте (по умолчанию)
Squash and mergeВся ветка сжимается в один коммитВетка с «мусорными» коммитами; чистая история main
Rebase and mergeКоммиты ветки переезжают в main без merge-коммитаЛинейная история без лишних коммитов

Полезные фишки

  • Draft PR — черновик: ревью не запросят, пока не переведёте в Ready.
  • Магия в описании: Closes #42 — при merge автоматически закроет issue №42. Также работают Fixes, Resolves.
  • Linked issues — привязка задач в боковой панели.
  • Files changed → Review changes — общий комментарий или request changes.
  • Suggested changes — ревьюер предлагает готовую правку, автор применяет одним кликом.
  • Auto-merge — мерж произойдёт сам, как только пройдут все проверки.
  • <tab> «Conversation / Commits / Checks / Files changed» — разные разрезы одного PR.
# Управление PR из терминала (GitHub CLI)
gh pr list
gh pr status
gh pr view 12 --web
gh pr checkout 12          # забрать ветку PR к себе
gh pr review 12 --approve
gh pr merge 12 --squash --delete-branch
gh pr checks 12
💡 На этом сайте

Этот учебник разрабатывается именно по такому циклу: изменения в ветке → PR → GitHub Actions собирает сайт и проверяет сборку. Загляните во вкладки Pull requests и Actions нашего репозитория.

10 Issues: задачи и баг-трекер

Issue — универсальная карточка работы: баг, новая фича, вопрос, задача на рефакторинг. Каждому issue присваивается номер, на который можно ссылаться из любого места платформы (#42).

Анатомия issue

  • Title + description — с Markdown, скриншотами, записями видео (через поле комментария).
  • Labels — цветные метки: bug, enhancement, good first issue, help wanted.
  • Assignees — ответственные.
  • Milestones — группы задач с целевой датой (релиз 2.0).
  • Sub-issues и задачи-чекбоксы — декомпозиция крупной работы.
  • Linked pull requests — автоматическая связь PR ↔ issue.

Шаблоны issues

Создайте папку .github/ISSUE_TEMPLATE/ с файлами:

# .github/ISSUE_TEMPLATE/bug_report.yml (форма для нового формата issues)
name: 🐛 Сообщение об ошибке
description: Опишите проблему, которую нужно исправить
labels: [bug]
body:
  - type: textarea
    id: what-happened
    attributes:
      label: Что произошло?
      placeholder: Опишите шаги воспроизведения…
    validations:
      required: true
✅ Триады open source

11 Projects: планирование и канбан

GitHub Projects — гибкая система планирования (новая версия, replaced старые Boards). Таблица или доска, куда можно добавить issues, PR, черновики и заметки из нескольких репозиториев сразу.

Два представления

  • Table — гибкая таблица: сортировка, группировка по любому полю, Excel-подобные фильтры.
  • Board (kanban) — колонки: Todo → In progress → Done. Карточки перетаскиваются мышью.
  • Roadmap — диаграмма Ганта по полю даты.

Ключевые понятия

ПонятиеОписание
ItemКарточка: issue, PR, черновик или заметка
Custom fieldСвоё поле: Priority (select), Estimation (number), Start/End date
ViewРазрез одной доски: «Баги по приоритету», «Спринт 12», «Roadmap»
WorkflowАвтоматизация: «при PR merged → колонка Done»

Автоматизации из коробки

  • Issue создан → добавить в проект;
  • PR открыт → статус «In progress»;
  • PR закрыт/смёржен → статус «Done»;
  • Нравится реализовывать свои: через GitHub Actions + actions/add-to-project.

12 GitHub Actions: CI/CD и автоматизация

GitHub Actions — встроенный движок автоматизации. Он запускает workflows (сценарии) по событиям: push, PR, релиз, расписание, комментарий и даже звёздочка. Именно Actions пересобирает эту страницу при каждом изменении.

Терминология

ТерминЗначение
WorkflowФайл .github/workflows/*.yml — весь сценарий
Event / on:Триггер: push, pull_request, schedule, workflow_dispatch…
JobГруппа шагов; джобы выполняются параллельно (если не указано needs:)
StepШаг: shell-команда (run:) или готовый экшен (uses:)
RunnerВиртуальная машина, где выполняется джоб (ubuntu-latest и др.)
ActionПереиспользуемый шаг с Marketplace (чужой или ваш)
ArtifactФайлы, сохранённые после джоба (сборка, отчёты)
SecretСекретная переменная (ключи API, токены)

Минимальный workflow

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]        # только для main
  pull_request:             # для всех PR
  workflow_dispatch:        # кнопка Run workflow в UI

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Забрать код
        uses: actions/checkout@v4

      - name: Установить Node
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Установить зависимости
        run: npm ci

      - name: Тесты
        run: npm test

  deploy:
    needs: test                 # ждать завершения test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Деплой!"

Матрица сборок — тест на нескольких ОС и версиях

jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20, 22]
        exclude:
          - os: macos-latest
            node: 18
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}

Секреты и переменные

steps:
  - name: Деплой на сервер
    run: ./deploy.sh
    env:
      API_KEY: ${{ secrets.DEPLOY_API_KEY }}
      ENV_NAME: ${{ vars.ENVIRONMENT_NAME }}

Секреты задаются в Settings → Secrets and variables → Actions. В логах они маскируются звёздочками.

⚠️ Встроенный GITHUB_TOKEN

В каждом workflow доступен автоматически создаваемый ${{ secrets.GITHUB_TOKEN }} с правами на текущий репозиторий. Для API-вызовов к самому репозиторию используйте его, а не персональный токен.

Популярные события триггеров

СобытиеКогда срабатывает
on: pushЛюбой push (можно фильтровать ветки и пути)
on: pull_requestСоздание/обновление PR
on: scheduleПо cron: - cron: '0 3 * * *' (каждый день в 03:00 UTC)
on: releaseПубликация релиза
on: issuesСоздание/изменение issues
on: workflow_dispatchРучной запуск (с параметрами inputs)
on: workflow_callВызов из другого workflow (reusable workflows)
✅ Marketplace

Не пишите с нуля то, что уже есть: GitHub Marketplace — тысячи готовых экшенов: деплой на любой хостинг, линтеры, релизы, уведомления в Telegram/Slack.

13 GitHub Pages: бесплатный хостинг сайтов

GitHub Pages публикует статические файлы (HTML, CSS, JS) прямо из репозитория — бесплатно и без своего сервера. Так можно опубликовать сайт-визитку, документацию проекта или, например, страницу этого учебника.

Три типа сайтов

ТипURLКак включить
Личный сайтusername.github.ioРепозиторий с именем username.github.io
Сайт проектаusername.github.io/repoSettings → Pages → источник
Сайт организацииorgname.github.ioАналогично личному

Способы публикации

  1. Из ветки — классика: выберите ветку main и папку / (root) или /docs — GitHub сам раздаёт файлы.
  2. Через GitHub Actions (рекомендуется) — полный контроль: можно сначала собрать проект (Next.js, Vite, Jekyll), потом опубликовать артефакт.

Стандартный workflow деплоя на Pages

# .github/workflows/pages.yml — классическая схема деплоя статического сайта
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write          # право публиковать Pages
  id-token: write       # OIDC-токен для deploy-pages

concurrency:
  group: pages
  cancel-in-progress: true   # новое издание отменяет старую сборку

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
✅ Кастомный домен

Положите файл CNAME с вашим доменом в корень сайта и настройте DNS (CNAME-запись на username.github.io). HTTPS включится автоматически через Let's Encrypt.

💡 Ограничения

Pages — только статика: 1 ГБ на сайт, лимит 100 сборок в час. Серверный код (Node, PHP, базы) не выполняется — для этого есть другие платформы или свои серверы.

14 Tags и Releases

Tag — метка на конкретном коммите (обычно версия: v1.2.0). Release — оформленная публикация на GitHub: описание релиза + прикреплённые файлы (бинарники, архивы).

# Аннотированный тег (рекомендуется для версий)
git tag -a v1.0.0 -m "Первый стабильный релиз"
git push origin v1.0.0

# Удалить тег
git tag -d v1.0.0
git push origin :refs/tags/v1.0.0
# Release через gh CLI
gh release create v1.0.0 --title "Версия 1.0.0" --notes "Список изменений: …"
gh release create v1.1.0 dist/app.zip dist/app.sha256
gh release list
gh release view v1.0.0

Семантическое версионирование (SemVer)

Формат MAJOR.MINOR.PATCH:

  • MAJOR — ломающие изменения API;
  • MINOR — новая функциональность с обратной совместимостью;
  • PATCH — исправления багов.

Автоматический релиз через Actions

# .github/workflows/release.yml — релиз по пушу тега
name: Release
on:
  push:
    tags: ['v*']
jobs:
  build-and-release:
    runs-on: ubuntu-latest
    permissions:
      contents: write          # право создавать release
    steps:
      - uses: actions/checkout@v4
      - run: ./build.sh
      - uses: softprops/action-gh-release@v2
        with:
          files: dist/*

16 Codespaces: облачная среда разработки

Codespaces — готовый VS Code + настроенное окружение, работающий в облаке. Открывается в браузере за минуту, для любого репозитория, с любым компьютера.

Зачем

  • Не тратить час на настройку окружения под чужой проект;
  • Единая среда для всей команды — «у всех работает»;
  • Слабый ноутбук, Chromebook, планшет — код пишется в браузере;
  • Изолированность: несколько проектов с разными версиями инструментов.

Как это работает

  1. На странице репозитория: Code → Codespaces → Create codespace on main.
  2. GitHub поднимает контейнер, клонирует код, ставит зависимости, открывает редактор.
  3. Внутри — терминал, git, расширения, порты с пробросом (localhost:3000 открывается через проброс в браузер).

Конфигурация проекта: devcontainer

# .devcontainer/devcontainer.json
{
  "name": "Node.js",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:20",
  "postCreateCommand": "npm install",
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
    }
  },
  "forwardPorts": [3000]
}
⚠️ Квота

Бесплатно: 120 core-часов и 15 ГБ хранения в месяц (например, 2-ядерный контейнер — 60 часов работы). Останавливайте codespace: Codespaces → … → Stop — иначе часы тикают дальше.

18 Безопасность репозитория

Вкладка Security в репозитории — командный центр безопасности. Большинство инструментов включены бесплатно для публичных репозиториев.

Инструменты

ИнструментЧто делает
Dependabot alertsПредупреждает об уязвимостях в зависимостях (npm, pip, Maven…)
Dependabot version updatesАвтоматические PR «обновить зависимость до свежей версии»

Включить Dependabot

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm        # npm, pip, maven, docker, github-actions…
    directory: /
    schedule:
      interval: weekly
    open-pull-requests-limit: 10

Secret scanning и push protection

Включите Settings → Code security and analysis → Secret scanning + Push protection. При попытке запушить коммит с ключом AWS GitHub остановит push и покажет, где секрет. Утечка секрета: 1) отозвать ключ, 2) удалить из истории (например, git filter-repo), 3) сменить все затронутые креды.

🚨 Золотые правила

• Секреты — только в Secrets, не в коде.
• .env — в .gitignore.
• Используйте минимально-необходимые токены (fine-grained PAT).
• Включите 2FA и branch protection.

23 API и Webhooks

REST API

Всё, что вы видите на сайте, доступно через REST API. Базовый адрес: https://api.github.com.

# Информация о репозитории
curl -H "Authorization: Bearer $GITHUB_TOKEN" \
     https://api.github.com/repos/zigorminsk-debug/githab-books

# Создать issue из скрипта
curl -X POST -H "Authorization: Bearer $GITHUB_TOKEN" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/repos/USER/REPO/issues \
     -d '{"title": "Автотест упал", "body": "Логи: …", "labels": ["bug"]}'

GraphQL API

Для сложных запросов — GraphQL v4: одним запросом достать репозитории, PR, ревью и статусы без множества REST-вызовов.

Webhooks

Webhook — уведомление: GitHub сам пингует ваш сервер POST-запросом, когда что-то случилось (push, issue, PR). Настраиваются в Settings → Webhooks.

  • Типовые применения: сборка на своём CI, деплой на свой сервер, интеграция с чатом.
  • Проверяйте подпись X-Hub-Signature-256 (HMAC с вашим secret), чтобы убедиться, что запрос пришёл от GitHub.
  • Логи доставки и повторная отправка — прямо на странице webhook.
✅ GitHub Apps

Для серьёзных интеграций вместо PAT используют GitHub Apps: собственная «служба» с тонкими правами, установленная на нужные репозитории. Так работают GitHub Actions, Dependabot и сторонние боты.

24 Шпаргалка: все команды в одном месте

Ежедневный минимум

git status                  # что изменилось
git add .                   # добавить всё в staging
git commit -m "сообщение"   # сохранить снимок
git pull                    # забрать изменения с GitHub
git push                    # отправить изменения на GitHub
git log --oneline -10       # последние 10 коммитов

Ветки

git switch -c feature/x     # создать + перейти
git switch main             # вернуться на main
git merge feature/x         # влить ветку
git branch -d feature/x     # удалить локально
git push origin --delete feature/x  # удалить на GitHub

Отмена и исправление

git restore file            # отменить правки файла
git restore --staged file   # убрать из staging
git commit --amend          # дописать в последний коммит
git revert <hash>           # отменить коммит новым коммитом
git reset --hard origin/main  # ⚠️ привести ветку к состоянию GitHub
git clean -fd               # ⚠️ удалить untracked-файлы

GitHub CLI

gh repo clone user/repo     # клонировать
gh pr create --fill         # создать PR
gh pr checkout 12           # взять чужой PR
gh pr merge 12 --squash     # слить со сжатием
gh run watch                # следить за CI
gh issue create -t "…" -b "…"
✅ Алиасы для скорости
git config --global alias.st status
git config --global alias.co checkout
git config --global alias.lg "log --oneline --graph --all"
